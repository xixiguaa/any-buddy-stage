# 从 0 实现一个类似 CodeBuddy 的本地 AI Agent 工作台：任务、权限和运行时是怎么组织起来的？

> 不把 Agent 做成一次性聊天框，而是把它做成可追踪、可恢复、可维护的本地工作流。

项目地址：https://github.com/xixiguaa/any-buddy-stage

最近我在做一个开源项目，叫 **AnyBuddy**。

它不是一个新的 AI 聊天框，也不是简单套一层模型 API 的桌面壳子。我的目标是把 AI Agent 从“临时对话”推进到“本地工作台”：每个任务都有自己的工作区、模型配置、专家预设、技能、运行时事件、权限状态和历史记录。

换句话说，我想让 Agent 不只是帮你回答一句话，而是可以围绕一个长期任务持续工作，并且这个过程是可以查看、可以暂停、可以恢复、可以审计的。

这个项目最早的灵感，来自我对腾讯 CodeBuddy 这类 AI 编程工作台形态的观察。它让我意识到：Agent 产品不一定只能是一个聊天入口，它完全可以围绕任务、项目、工具和工作流来组织。但当时我没有找到一份足够完整、可以深入研究和二次开发的开源实现，于是决定自己做一个。

AnyBuddy 和 CodeBuddy 没有官方关系，也不是对某个产品的复刻。我更想做的是一个开放的本地优先 Agent 工作台，让更多人可以看到它的实现方式、参与它的架构讨论，并把自己的工作流沉淀进去。

## 为什么想做这个项目

现在很多 AI 编程或办公助手，使用体验仍然像一次性聊天。

你把上下文丢进去，它给你一个回答；你继续追问，它可能还能接上；但当任务变长、工具调用变多、文件修改变复杂以后，问题就会慢慢出现：

- 上下文散落在聊天记录里，很难沉淀成稳定任务。
- Agent 当前做到了哪一步，不够清楚。
- 工具调用、命令执行、审批状态，经常被藏在黑盒里。
- 长任务一旦中断，很难自然恢复。
- 不同专家能力、技能和工作区上下文，很难组织成同一个流程。
- 本地文件、模型配置和运行记录之间缺少一个统一工作台。

我不太想把 Agent 当成“更聪明的聊天机器人”。对复杂工作来说，它更像一个运行中的任务系统：需要状态、上下文、权限、事件、历史和可观察性。

这就是 AnyBuddy 的出发点。

## AnyBuddy 是什么

**AnyBuddy 是一个本地优先的 AI Agent 工作台。**

它基于 Electron Forge、Vite、React、TypeScript 和 SQLite 构建，主进程负责运行时、文件系统、持久化和工具调用，渲染进程专注于桌面交互界面。

在 AnyBuddy 里，你可以围绕“任务”组织 Agent 工作流：

- 创建一个任务。
- 绑定工作区上下文。
- 选择模型。
- 选择工作模式。
- 选择权限模式。
- 加载专家预设和技能。
- 查看运行时事件。
- 处理本地命令审批。
- 继续历史任务。

这些信息不会只停留在临时聊天窗口里，而是会被本地持久化下来，成为可以继续维护的工作流记录。

## 核心设计：从 Chat 到 Workspace

我最想解决的问题，是把 Agent 的产品心智从 Chat 往 Workspace 推一步。

普通 Chat UI 更适合短问题，比如解释一段代码、生成一个函数、回答一个概念。但当你希望 Agent 参与真实项目时，它需要知道：

- 当前任务是什么。
- 任务绑定了哪个工作区。
- 当前选择了哪个模型。
- 允许它读写哪些内容。
- 是否需要审批命令。
- 执行过程中调用了哪些工具。
- 哪些输出只是流式中间态，哪些结果已经完成并持久化。

所以 AnyBuddy 把体验组织在任务之上，而不是组织在一条孤立对话之上。

每个任务都可以携带自己的模型、技能、连接器、权限、运行事件和历史消息。这样 Agent 的工作过程不只是“生成文本”，而是逐步变成一个可以观察和管理的本地系统。

## 目前已经有的能力

AnyBuddy 当前重点围绕几个方向建设。

### 本地优先持久化

核心任务、消息、工作区、运行记录、事件和审批状态会写入本地 SQLite。

这意味着 Agent 工作流不需要完全依赖远端服务保存状态。对个人开发者、本地项目、隐私敏感任务来说，本地优先会更安心，也更容易调试。

### 桌面端工作台

AnyBuddy 是 Electron 桌面应用。

主进程负责文件系统、运行时服务、SQLite、模型调用和工具注册；渲染进程负责 React UI 和 Zustand 状态管理；preload 层通过 `window.anybuddy` 暴露安全桥。

这个边界设计是刻意的：桌面应用需要访问本地能力，但 UI 层不应该随意直接碰 Node 或 Electron 主进程 API。

### 任务式 Agent 工作流

项目不是围绕“开一个聊天窗口”来设计，而是围绕任务创建、任务继续、运行状态和事件流来组织。

一个任务可以被暂停、继续、查看历史，也可以绑定不同的专家能力和工作区上下文。对长任务来说，这比单纯聊天更接近真实工作方式。

### 可见运行时事件

我希望用户能看到 Agent 正在发生什么。

所以 AnyBuddy 会把工具调用、审批、执行进度、运行事件等信息展示出来，而不是只给最终回答。

Agent 越能做事，透明度就越重要。尤其当它开始读写文件、执行命令、调用工具时，用户需要知道它做了什么、为什么做、现在卡在哪里。

### 工作模式和权限模式分离

AnyBuddy 把“Agent 应该怎么工作”和“Agent 被允许做什么”分开配置。

工作模式包括：

- `ask`：偏问答、解释、检索和分析。
- `plan`：偏拆解任务、制定方案和确认路径。
- `craft`：偏直接实现、编辑文件和完成验证。

权限模式包括：

- `read_write`：允许读写工作区，但执行本地命令前需要用户确认。
- `full_access`：允许更完整的本地访问，适合用户明确知道当前任务可信时使用。

这个拆分很重要。因为“我希望 Agent 主动帮我实现”和“我允许 Agent 执行本地命令”不是同一件事。

### 专家预设和 Skills

AnyBuddy 支持专家预设和全局技能目录。

技能可以从 `~/.anybuddy/skills/<skillId>/SKILL.md` 加载，并在运行时镜像到当前工作区缓存。这样不同类型的任务可以加载不同的工作方式、工具约束和上下文说明。

长期来看，我希望 AnyBuddy 不只是一个 Agent Shell，而是一个能沉淀个人工作流的本地系统。

## 技术栈

当前项目主要使用：

- Electron Forge + Vite
- React 19
- TypeScript
- Zustand
- Ant Design
- SQLite / better-sqlite3
- LangChain / DeepAgents
- OpenAI-compatible model config

代码结构大致分为：

```text
src/
  main/       Electron 主进程、IPC 处理、仓储、运行时服务
  preload/    暴露给渲染进程的安全桥
  renderer/   React 界面、页面、组件、状态和样式
  shared/     共享类型、IPC 契约和跨进程工具
docs/         贡献文档、架构说明和设计草案
```

如果你对 Electron、Agent Runtime、IPC 边界、本地持久化、工具审批流这些方向感兴趣，应该会比较容易从项目里找到可以讨论和贡献的点。

## 它和普通 AI Chat 有什么不同

我对 AnyBuddy 的定位不是“再做一个 ChatGPT 客户端”。

普通 AI Chat 更像即时对话，而 AnyBuddy 更像任务工作台：

| 维度     | 普通 AI Chat       | AnyBuddy                         |
| -------- | ------------------ | -------------------------------- |
| 组织方式 | 对话               | 任务                             |
| 上下文   | 聊天历史为主       | 工作区、模型、技能、专家、连接器 |
| 状态     | 弱状态             | 本地持久化状态                   |
| 工具调用 | 经常不可见或弱可见 | 运行时事件可见                   |
| 长任务   | 容易中断和失忆     | 面向继续执行和恢复               |
| 权限     | 常与能力混在一起   | 工作模式和权限模式分离           |
| 目标     | 回答问题           | 维护 Agent 工作流                |

这也是我认为 Agent 产品接下来会变得有意思的地方：不是模型回答得更长，而是整个工作过程变得更可控。

## 当前状态

AnyBuddy 还处在早期阶段。

现在已经有基础的桌面应用结构、任务模型、本地持久化、运行时服务、专家和技能相关设计，以及一些围绕 DeepAgents 的执行层改造。

但它还不是一个“完成品”。接下来我会继续补：

- 更完整的截图和演示 GIF。
- 更稳定的任务运行体验。
- 更清晰的专家配置界面。
- 更好用的 Skills 管理。
- MCP / connector 相关能力。
- 测试和文档补充。
- 打包分发体验。

如果你现在点进去看，它更像一个正在生长中的开源工作台，而不是一个已经包装完美的商业产品。

这也正是我选择现在开源和分享的原因：我希望它在还可以被塑形的时候，就获得真实使用者和开发者的反馈。
